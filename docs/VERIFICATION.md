## Что покрыто тестами

- Создание и публикация нового салона через API, настройка каталога и расписания.
- Конкуренция двадцати подтверждений за один слот; повтор идемпотентной команды.
- Подтверждение пересечения в другом салоне, сохранение исходного визита при неудачном переносе.
- Ограничение CRM по салонам, запрет денежных полей мастеру, отзыв роли, устаревшие версии.
- Невозможность завершить будущий визит; подавление напоминаний после отмены; снимки цены.
- Двухсторонняя привязка ручной карточки, исключение перерывов из слотов.
- Лояльность: порог, следующий цикл, исключение старой истории, нулевых цен, отмен и неявок.
- Однократное начисление при параллельных завершениях; однократный резерв награды в разных слотах.
- Бесплатный перенос, возврат при отмене и неявке, использование без новой отметки.
- Недоступность чужой награды, другой услуги и другого салона; запрет совмещения с купоном.
- Исправление завершения, отзыв неиспользованной награды, сохранение остальных отметок.
- Блокировка исправления с зарезервированной/использованной зависимой наградой.
- Пауза программы, фиксация условий после отметки, настройки только владельцем.
- Сохранение награды ручного клиента после подтверждённой привязки MAX.
- Защита webhook секретом, сохранение событий, порядок stop/start/remove.
- Правильные ссылки из уведомлений для клиента, владельца и назначенного мастера.
- Согласование партнёрской версии, защита хеша, однократная выдача/резерв/списание купонов, согласие клиента и независимые паузы сторон.
- Браузер: вход клиента и владельца, карточки прогресса, настройки, лояльность в CRM, расчёт записи; отсутствие горизонтального переполнения на мобильном экране.

Для переходов, требующих прошедшего времени, **тесты** создают синтетические прошлые интервалы в отдельной базе `_test`. Production API не позволяет произвольно переносить визит в прошлое или обходить время завершения.

## Что осталось проверить в окружении запуска

1. Освободить место на системном диске и восстановить Docker Engine. Затем выполнить `ops/scripts/demo-up.ps1` или `demo-up.sh` и проверить готовность всех контейнеров.
2. Проверить production-конфигурацию на отдельном сервере с настоящим доменом, сертификатами и секретами; выполнить `max:check`.
3. Пройти сценарий настоящего MAX по `MAX-SETUP.md`, включая доставку, stop/restart, ссылки и два типа клиентов.
4. Провести нагрузочные измерения и полную приёмку по ТЗ. Сейчас запись защищена общей транзакционной блокировкой команд; масштабируемость под большой поток не измерялась.
5. Перед работой с реальными клиентами определить оператора данных, сроки хранения, резервное копирование и порядок разбора использованных наград при ошибочной отметке исходного визита.

Для обхода заполненного C: тесты и сборка использовали `.local/tmp` и `.local/npm-cache` на D:. Чужие файлы и контейнеры не удалялись. Browser mock и успешные локальные тесты не заменяют подтверждение работы настоящего MAX.
