# Подключение настоящего MAX

## 1. Что подготовить

Нужны бот с действующим токеном, его точное имя, право подключить мини-приложение, сервер с публичным доменом и HTTPS. Домен должен указывать на сервер; входящие TCP-порты 80 и 443 — быть доступны. В Docker production Caddy обслуживает сайт и сертификат.

Требования проверены по официальной документации 21.09.2026: [подключение мини-приложения](https://dev.max.ru/docs/webapps/introduction), [API MAX](https://dev.max.ru/docs-api), [webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions). Действующий API-адрес — `https://platform-api2.max.ru`. Токен передаётся заголовком Authorization. Webhook требует HTTPS на порту 443 и доверенный сертификат.

## 2. Куда вставить токен

В корне проекта уже есть папка `secrets`. Создайте в ней:

```text
secrets/max_bot_token.txt       только настоящий токен бота, одна строка
secrets/max_webhook_secret.txt  отдельный случайный секрет webhook, одна строка
```

Токен берётся в настройках вашего бота на платформе MAX. Не вставляйте его в чат, React-код или URL. Используйте редактор файла, чтобы токен не оказался в истории команд.

Секрет webhook — не токен бота. Например, безопасную случайную строку можно получить командой и сохранить её в `max_webhook_secret.txt`:

```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

В Docker файлы доступны как `/run/secrets/max_bot_token` и `/run/secrets/max_webhook_secret`. Приложение читает их через `MAX_BOT_TOKEN_FILE` и `MAX_WEBHOOK_SECRET_FILE`. Оба файла исключены из Git; не включайте их в архив исходников.

## 3. Конфигурация рабочего сервера

Создайте личный `.env.production` из `.env.production.example`. Замените:

```dotenv
APP_ENV=production
MAX_MODE=real
PUBLIC_APP_URL=https://ваш-домен
SITE_ADDRESS=ваш-домен
MAX_BOT_NAME=имя_бота_без_символа_собака
MAX_API_BASE_URL=https://platform-api2.max.ru
POSTGRES_PASSWORD=случайный_пароль_администратора_БД
POSTGRES_RUNTIME_PASSWORD=другой_случайный_пароль_приложения
HTTP_PORT=80
```

Для паролей БД удобно использовать случайные hex-строки: их не нужно дополнительно кодировать для URL. `PUBLIC_APP_URL` указывайте без завершающего `/`, `SITE_ADDRESS` — без `https://` и пути. Не используйте демонстрационные пароли на рабочем сервере.

Запуск на **новом сервере с отдельными данными**:

```sh
docker compose --env-file .env.production -f compose.yaml -f compose.production.yaml up --build -d
docker compose --env-file .env.production -f compose.yaml -f compose.production.yaml ps
```

Демо-профиль не включается и синтетические пользователи не создаются. При первом входе реальный владелец создаёт свой салон через интерфейс. Не переключайте общую демо-базу в production: для рабочего развёртывания используйте отдельный сервер или отдельное Compose project name и volumes. Пароли существующей PostgreSQL-базы не меняются простым редактированием env — это отдельная административная операция.

Откройте `https://ваш-домен/health/ready`: должен ответить сервер. Убедитесь, что `worker.lastHeartbeat` обновляется. Получение сертификата требует корректного DNS и доступности сервера снаружи.

## 4. Проверить токен и зарегистрировать webhook

Сначала выполните только проверку:

```sh
docker compose --env-file .env.production -f compose.yaml -f compose.production.yaml exec api npm run max:check
```

Команда обращается к `/me`, сравнивает имя бота с `MAX_BOT_NAME` и проверяет существующие подписки. Сам токен не выводится. В mock-режиме скрипт отказывается выдавать проверку за настоящую.

Когда публичный HTTPS уже работает, зарегистрируйте webhook:

```sh
docker compose --env-file .env.production -f compose.yaml -f compose.production.yaml exec api npm run max:check -- --subscribe
```

Это создаёт подписку на `https://ваш-домен/integrations/max/webhook`. Скрипт не удаляет подписки других систем. У API есть проверка `X-Max-Bot-Api-Secret`; событие сначала сохраняется в PostgreSQL и только затем подтверждается MAX.

### Если возникает ошибка TLS

В актуальной [документации API](https://dev.max.ru/docs-api) отдельно указана настройка доверия к сертификату Минцифры. Получайте нужную цепочку только из проверенного официального источника и устанавливайте в доверие того окружения, откуда работает сервер. Не отключайте проверку TLS.

Для Node.js поддерживается `NODE_EXTRA_CA_CERTS`. Например, сохраните доверенный PEM в `secrets/max-ca.pem`, создайте дополнительный Compose-файл:

```yaml
x-trust: &trust
  environment:
    NODE_EXTRA_CA_CERTS: /run/secrets/max_ca
  secrets:
    - max_ca
services:
  api:
    <<: *trust
  worker:
    <<: *trust
  migrate:
    <<: *trust
secrets:
  max_ca:
    file: ./secrets/max-ca.pem
```

Подключайте этот файл последним через ещё один `-f`. Он дополняет production-конфигурацию. Доверие к исходящему API MAX и HTTPS-сертификат вашего сайта — разные настройки; проверять нужно обе.

## 5. Подключить mini-app к боту

В кабинете MAX откройте настройки своего бота и укажите URL мини-приложения `https://ваш-домен`. После сохранения откройте его из диалога с ботом. Проект подключает [MAX Bridge](https://dev.max.ru/docs/webapps/bridge) и проверяет входные данные на сервере по [алгоритму MAX](https://dev.max.ru/docs/webapps/validation).

Ссылка входа: `https://max.ru/ИМЯ_БОТА?startapp=home`. Ссылки отдельных салонов и QR доступны в настройках салона. Реальная роль владельца создаётся после создания салона, роли сотрудников — после принятия приглашения; параметры URL прав не дают.

## 6. Проверить сценарий в MAX

1. Откройте бота и запустите его, затем mini-app. Повторите в мобильном и веб-клиенте MAX.
2. Создайте салон, услугу, мастера и график, опубликуйте витрину.
3. Другим аккаунтом запишитесь на свободный слот и откройте карточку визита.
4. В профиле клиента включите сервисные сообщения и напоминания нужного салона. Проверьте событие и сообщение бота.
5. Проверьте ссылку из сообщения для клиента и рабочего сотрудника.
6. Проверьте перенос, отмену и отсутствие старых напоминаний после изменения записи.
7. Для лояльности задайте небольшой порог до первой отметки. После реальных завершённых визитов используйте награду и проверьте итог 0 ₽.
8. Остановите бота, проверьте прекращение отправок, затем запустите снова. Старые отменённые доставки не должны воскреснуть.

Не меняйте часы сервера ради демонстрации завершения. Для тестов переходов используются отдельные синтетические данные; они не заменяют реальный сценарий в MAX.

## 7. Эксплуатация

Для всех production-команд сохраняйте одинаковые `--env-file` и список `-f`:

```sh
docker compose --env-file .env.production -f compose.yaml -f compose.production.yaml logs --tail=100 api worker
docker compose --env-file .env.production -f compose.yaml -f compose.production.yaml down
```

Токен и webhook-секрет должны совпадать у API, worker и зарегистрированной подписки. При смене токена перезапустите API/worker; при смене webhook-секрета также повторно зарегистрируйте подписку. Проверку реального бота нельзя считать пройденной только по успешному локальному демо.
