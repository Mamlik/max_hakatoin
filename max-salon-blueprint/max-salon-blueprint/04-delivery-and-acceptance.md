# 04. План разработки, тесты, развёртывание и сдача

## 1. Как организовать работу

Потоки ниже — роли будущей команды из входного дополнения, а не уже запущенные исполнители. Один человек-координатор принимает общие контракты, миграции и интеграцию. Наличие четырёх потоков не означает четыре независимых несовместимых проекта.

| Поток | Основная зона | Необходимый результат |
|---|---|---|
| A — платформа и MAX | Auth, tenant/access, MAX adapters, inbox/outbox/delivery, CI/infra | Проверенная идентичность, изоляция, воспроизводимая инфраструктура и бот-канал |
| B — операции салона | Каталог, график, bookings, CRM и связи клиентов | Атомарная запись/перенос, рабочая CRM, чистые контракты предметной области |
| C — frontend | Общий shell, все клиентские/рабочие экраны, MAX UI/Bridge | Доступный мобильный и веб-путь для каждой P0 функции |
| D — партнёрства и аналитика | Версии, согласования, vouchers, метрики, интеграционный набор | Согласованные условия, корректные расчёты и проверяемые инварианты |

A владеет общими middleware, B — Booking schema, D — Campaign/Voucher schema; схему БД и contracts вливает координатор. C не придумывает fallback-данные для отсутствующего API: использует согласованные MSW fixtures и отмечает временную mock-границу. Каждый поток пишет проверки своей логики; общая QA-проверка не перекладывается целиком на D.

PR маленький и законченный: контракт → миграция → сервер → тесты → экран, если входит в задачу. Если изменения разделены на PR, зависимость явно указана. Новая миграция получает порядковый номер после интеграции; ранее применённые миграции не редактировать.

## 2. Что решить до параллельной реализации

Координатор фиксирует в `docs/adr/`:

- ADR-001: выбранные технологии, реальные package versions, Docker digests, лицензии, результат совместимой сборки.
- ADR-002: auth/session/MAX IDs и подтверждённая форма initData.
- ADR-003: tenant boundaries, role projections, composite FK.
- ADR-004: запись, порядок locks, idempotency и warning challenge.
- ADR-005: campaign versioning, coupon invariants, корректировки исходов.
- ADR-006: outbox, delivery, rate limiter, восстановление и пределы гарантий.
- ADR-007: график, snapshots, timezone и определения метрик.

В общем контракте сначала заморозить enums status/role/error, UUID/время/деньги, envelope, CreateBooking/Quote/Reschedule/Complete, ClientBooking/StaffBooking, CampaignVersion/Voucher, EventEnvelope. Изменение через PR с перечислением потребителей и миграцией.

## 6. Тестовая стратегия

Unit проверяет правила, которые можно выразить без IO: интервалы, money, state transitions, permission predicates, consent, TTL, warning fingerprint, формулы. Fake clock обязателен; не делать тесты, зависящие от системной даты.

Integration использует настоящий PostgreSQL 17 с расширениями и Redis. SQLite/in-memory repository не докажут row lock, constraint и crash recovery. Параллельные тесты используют независимые соединения и barrier, чтобы запросы действительно столкнулись до commit.

Browser E2E — Chromium/WebKit в Playwright на известном fixture dataset и dev MAX adapter. Native mobile/web MAX smoke — вручную на тестовых аккаунтах с реальными подписанными payload и реальной доставкой. Bridge mock не входит в доказательство платформенного AC21.

### 6.2. Дополнительные обязательные тесты

- Auth: изменённый user/hash, duplicate key, payload старше 3600s, +61s в будущем, replay с прежним expiresAt, int64 больше JS safe integer, Unicode и percent encoding.
- Idempotency: одинаковый key+body; другой body/version; concurrent pending 202; сбой до/после commit; fence stale executor; >24h и >30d; после отзыва роли saved response недоступен.
- Scheduling: стык интервалов, длинная услуга через перерыв, исключение closed/replace, любой мастер, смена timezone/DST, конкурентное изменение графика и booking.
- Клиентский overlap: два параллельных бронирования в разных tenant, новый конфликт после предупреждения, challenge для другого actor/слота/version, подтверждение staff без раскрытия данных.
- Consent: все сочетания global/source/service/offer/reminder/channel; отзыв между постановкой и отправкой; согласие после completed не выдаёт купон.
- MAX channel: повтор bot_stopped+dialog_removed, started старее stop, равный timestamp, новый started с новой generation, отсутствие catch-up рассылки, API accepted не равен read.
- Queue: несколько worker, лимиты в любом 1000ms окне, 429 с/без Retry-After, timeout unknown, permanent recipient error, глобальный token error, crash sending, Redis reset.
- Campaign: active версия остаётся при draft/proposed новой; concurrent accept/edit; limit нельзя опустить ниже total; pause обеих сторон; irreversible ended; обе стороны published проверяются при выдаче.
- Coupon: source completion duplicate/correction, одновременно claim/expiry/cancel, reserve после expiry, новый start за сроком, reserved completion после expiry, redeemed невозможно разиспользовать.
- Corrections: owner-only; no_show→completed с купоном, использованным в другом визите; completed→cancelled с reserved/redeemed следствием отклонён; исправление не выдаёт новые предложения.
- Analytics: zero denominator, нет исторического snapshot, визит через границу периода, сохранённый denominator после смены будущего графика, повтор событий не удваивает metrics, cohort выдачи ≠ период погашения.
- Media/CRM: чужой draft-image, опасный файл с поддельным MIME, пересланная link-ссылка без staff confirmation, существующий user у другой карточки, смена личного имени не редактирует заметку.

### 6.3. Нагрузочный протокол

Seed: минимум 10 tenant, 10 000 исторических bookings, разные статусы/мастера/кампании. Конкурентность: 20 авторизованных сессий, уникальные пользователи и роли; не 20 запросов одной закешированной страницы.

Профиль: 5 минут прогрева, 10 минут измерения; чтение календаря/слотов/CRM/личной ленты, создание/перенос/отмена на разных ресурсах. Доли запросов записать в отчёт. Отдельно hotspot-тест одного слота/купона — конфликт там ожидается, а не считается ошибкой сервера.

Проверяем p95 серверной обработки обычных read/write ≤2s, без сетевого времени клиента и MAX API; HTTP histogram на сервере и k6 end-to-end публикуем отдельно. Новое событие до постановки на отправку ≤30s, аналитика после команды ≤10s в здоровом контуре. Замер clean build ≤5 минут без первой загрузки base images — отдельный тест.

Отчёт содержит commit, hardware, версии образов, размер данных, профиль, p50/p95/p99, throughput, error rate, pool wait, queue lag и объяснение ожидаемых 409. Внешнюю недоступность MAX не маскировать как успешную доставку. До выполнения теста ни одно целевое число не называется достигнутым.

Скрипт запускается из корня будущего репозитория. Он проверяет Docker/Compose, создаёт только локальный demo env с синтетическим token при отсутствии, собирает контейнеры, ждёт health, выполняет migrations и идемпотентный seed, выводит адрес и test-role selector. Секреты реального MAX не нужны для локальной проверки.

Mock-bridge и mock MAX transport существуют только в demo profile. Синтетический initData подписывает отдельный mock issuer, backend проверяет обычную HMAC-логику с demo token. `APP_ENV=production` аварийно завершает запуск при MAX_MODE=mock/небезопасных demo credentials. Production API не предоставляет dev login endpoint. В staging для реального MAX обязательно MAX_MODE=real.

README ясно отделяет «локальное демо» от «проверки интеграции MAX». Одна команда не может зарегистрировать аккаунт, получить конкурсный токен и пройти внешнюю модерацию; эти предварительные условия описаны отдельно.

Остановка будущего контура: `docker compose down`; volumes по умолчанию сохраняются. `down -v` — отдельный осознанный reset demo, не стандартная остановка. Seed повторно не удаляет данные и не меняет рабочие tenant.

### 7.2. Конкурсный контур

Базовое размещение: одна Linux VM с 4 vCPU/8 GB RAM и SSD ≥60 GB — стартовая ресурсная гипотеза, подтверждается PERF-01. Один публичный домен; внешние порты 443 и при ACME 80; SSH ограничен ключами/доступом команды. PostgreSQL/Redis только в Docker network. Защищённые volumes для PostgreSQL, Redis, media, Caddy TLS.

Не утверждаем, что конкретный облачный аккаунт/хостинг уже есть. Исполнитель INF-02/OPS-01 выбирает доступную команде VM и проверяет выход на MAX из неё. Мультисерверность P0 не требуется. У media есть порт `MediaStorage`, чтобы позднее перейти на S3-совместимое хранилище без изменения бизнес-кода; сейчас используем local persistent volume и включаем его в backup.

Deployment pipeline:

1. CI на commit SHA проходит lint/typecheck/unit/integration/contract/e2e/build.
2. Собирает immutable images `api:<sha>`, `worker:<sha>`, `web-edge:<sha>`, формирует checksums/SBOM.
3. До миграции — backup БД и media; миграции применяются отдельным user и одной задачей под migration lock.
4. Поднять API/worker/edge, дождаться health, выполнить smoke на staging.
5. Проверить MAX `/me`, subscriptions и реальную тестовую доставку по согласованному D0 сценарию.
6. Сохранить release manifest: SHA, image digests, миграции, время, проверивший.

Rollback кода — на предыдущие images, только если схема совместима. Миграции проектировать expand/contract; destructive изменения не вносить в последний день. Если схема несовместима, сначала план восстановления на изолированном контуре, а не автоматический `migrate down` с потерей данных.

## 8. Наблюдаемость и восстановление

JSON-логи: requestId, operationId, eventId, tenantId где разрешён, aggregateId, durationMs, result/errorCode. Персональные тексты/телефон/initData/Authorization/invite token не логировать. Не копировать весь request.body ради отладки.

Метрики/пороги для staging:

- API p95, 5xx, DB connection wait, транзакционные retries и slot conflicts.
- `outbox_oldest_age_seconds`, `delivery_due_lag_seconds`, retry/failed/suppressed по причинам.
- timestamp последнего успешного webhook, **отдельно** факт наличия subscription, time since worker heartbeat.
- MAX latency/429/token/TLS errors; auth rejection и cross-tenant denial без лишних персональных меток.
- Истечение TLS, свободное место volumes, последняя успешная backup/restore проверка.

Отсутствие webhook-трафика само по себе не означает сбой: может не быть событий. Сбой — отсутствующая подписка, недоступный endpoint или провал smoke. Внешняя доставка degradation не отменяет возможность записаться; интерфейс показывает актуальное состояние и внутреннее событие.

Runbooks, которые требуется написать:

| Сбой | Первые действия |
|---|---|
| MAX 401 | Остановить исходящие retries глобально, проверить token и metadata через безопасный ops-client, после смены секрета перезапустить процессы и smoke |
| Webhook пропал | Проверить TLS/443/secret/inbox DB, GET subscriptions; восстановить подписку после устранения причины |
| Redis недоступен | Сохранения продолжаются в PostgreSQL, доставки приостановлены; поднять Redis, восстановить очередь reconciler, проверить generation/актуальность |
| Worker упал в sending | Lease recovery, пометка unknown; допускаемый повтор внешнего сообщения, без повторной бизнес-команды |
| БД недоступна | API mutations и webhook возвращают ошибку; не подтверждать запись/200 без сохранения |
| Ошибочная миграция | Остановить выпуск, оценить совместимость rollback, восстановить в отдельную БД и сверить данные |
| Ошибочное завершение визита | Действие owner correction в приложении, причина/аудит; не UPDATE руками |

Backup: ежедневный pg_dump custom + media manifest/файлы, шифрованная копия вне VM, сохранять минимум 7 суточных копий в пределах согласованного срока данных. Redis не является единственной резервной копией очереди. Один раз до реального пилота восстановить PostgreSQL/media на чистой VM, выполнить миграции до того же release и smoke без реальных рассылок. Начальные проектные цели RPO≤24h/RTO≤2h подлежат измерению, не являются заявленным SLA.

Для demo данные очищаются/обезличиваются после конца проверки +30 дней, включая sessions, inbox payload, idempotency, logs и копии по политике retention. Синтетические fixtures можно оставить, MAX IDs реальных тестировщиков — нет. Физическое удаление выполнять отдельной управляемой процедурой с учётом истории и ссылок; не делать каскадное удаление tenant пользовательской кнопкой.

## 9. Демо без скрытых операций

Fixtures: салоны A «Тестовая студия волос» и B «Тестовая студия маникюра», минимум по два мастера, активные услуги, недельные графики, исключение, ручная карточка, completed/cancelled/no_show история с известными суммами. Все данные с `is_test=true`, контакты вымышлены.

Реальные MAX-аккаунты тестировщиков связываются отдельным безопасным setup-процессом: авторизованный координатор/владелец назначает роли через продуктовые приглашения. Публичный seed не содержит реальные MAX IDs и token. Не создавать public endpoint «войти как владелец A» на конкурсном контуре.

Путь проверки:

1. Новый владелец создаёт третий салон с нуля, загружает изображение, добавляет услуги/мастера/график, публикует и открывает QR/ссылку.
2. Клиент входит по A, включает желаемые сервисные уведомления, создаёт запись, видит карточку/центр/сообщение бота.
3. Создаёт запись в B; открывает общий календарь, избранное и фильтры событий. В CRM A видна только история A.
4. Переносит/отменяет тестовый визит, показывает синхронное изменение и suppression старых reminders.
5. Owner A и Owner B добровольно включают партнёрство, согласуют одну версию A→B. Клиент заранее включает глобальное и source-разрешение.
6. Подготовленный тестовый визит A, время начала которого уже наступило, завершается **через UI**. Купон выдаётся обычным use case. Затем клиент бронирует B с купоном; для живого completion выбирается ближайший допустимый слот и ожидается его начало. Для короткой отдельной проверки redeem можно использовать заранее seeded reserved-визит с прошедшим началом, явно показав, что это тест другого перехода, а не полный живой A→B путь.
7. Показать redeem, историю версий, статистику и отрицательный сценарий повторного применения/cross-tenant.
8. Мастер отмечает только свой визит, admin видит операционные данные, owner отзывает доступ сотрудника. Проверить открытый экран после следующего запроса.

Время production-сервера ради демо не переводить. Раздельные fixtures для проверки переходов допустимы и маркируются; они не заменяют выполнение полного end-to-end пути на тестовом контуре. Не скрывать паузу до наступления времени визита и не обходить правило completion через БД.

## 10. Материалы выпуска и Definition of Done

README будущего приложения должен включать назначение, роли, основной путь, архитектуру, one-command demo, env/ports, MAX prerequisites, seed и реальные setup roles, ограничения, stop/restart, тесты и ожидаемые результаты. Все команды проверить на чистом окружении другим членом команды.

Комплект: исходники/commit hash, lockfile, Dockerfiles, compose/.dockerignore/.env.example, миграции, README, доступный bot/mini-app/HTTPS API, OpenAPI, DATA-API.yaml, результаты AC/load/MAX smoke, PDF-презентация по требованиям входного ТЗ. Формат DATA-API.yaml у организаторов в приложениях не дан: заполнить документ с method/path/role/params/expected response и отдельно сверить требуемую схему, не объявлять произвольный YAML официальным стандартом.

Первый служебный слайд содержит проверочные ссылки/версию/маршрут. Проверочные секреты, если требуются организаторами, только в закрытой версии материалов и по защищённому каналу; не в публичном Git. Условия и дедлайн конкурса сверить с исходным PDF/организаторами, поскольку PDF здесь не исследовался.

Задача готова, когда:

1. Покрыто требуемое поведение и ошибки, включая права/tenant.
2. Контракт и миграции совместимы с остальным проектом.
3. Серверные инварианты проверены подходящими тестами, frontend использует настоящий API.
4. События/аудит/идемпотентность реализованы для нужных команд.
5. Экран работает в узком размере, имеет loading/empty/error/noAccess.
6. Нет секретов/персональных данных в артефактах и логах.
7. Другая роль/повтор/конкурентный запрос не обходят ограничения.
8. PR принят и сценарий работает на общей сборке, а не только в ветке автора.
